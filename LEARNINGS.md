[gotcha] Accept-path residual (P2-FIX-2, /unslop M-A; final claim/finalize design): the C1 claim (`claim_advisor_proposal_for_accept`: row-locked pending->'accepting') GATES the entity writes — withdraw-vs-accept corruption is CLOSED (withdraw wins the FOR UPDATE first → claim RAISEs, or loses → its draft|pending guard no-ops vs 'accepting'). C6 stays intact (overlay mapper never relocated to SQL). Two residual paths, distinct — do NOT conflate:
(1) **claim-LOST path = genuinely ZERO writes.** If the claim RAISEs (withdraw/another op won the row lock, or status no longer 'pending'), `applyAcceptedProposalChanges` is never invoked → no `financial_*` row mutated at all. Fully data-safe.
(2) **post-claim mid-write-failure path = canonical data PARTIALLY MUTATED.** Once claimed, the TS writer applies entities sequentially (profile → investments → budget lines → goals). If a write fails partway, the earlier entities ARE already persisted (no surrounding DB txn — C6 forbids relocating the mapper into one SQL transaction, a ratified tradeoff). The proposal is parked in 'accepting' (C2 terminal, non-re-acceptable since claim requires 'pending' → no create-op duplication on a retry attempt), but the client's canonical data is left in a partially-applied state. Recovery is advisor-driven: rebuild a fresh proposal against the now-current baseline; there is NO auto-rollback or auto-recovery.
Also (3): the pre-claim re-baseline notify is best-effort; if it silently no-ops and the advisor never revisits, the proposal sits stale-`pending` indefinitely. Recommended future backstop (NOT built): a periodic sweep flagging proposals stuck in 'accepting' (partial mid-accept failure) or long-stale `pending` for advisor/ops attention. guard: none (doc-only; mitigations are the claim gate + fail-loud finalize + the terminal 'accepting' state from migration 20260605000000)

[gotcha] Pre-existing accept TOCTOU (P2-FIX-2, /unslop M-B; NOT introduced by C1–H3, explicitly out of this feature's scope): there is a microsecond window between `detectAcceptConflicts`' base read (`getProfileById`/`listInvestments`/`listBudgetLines`/`listFinancialGoals`) and the `claim_advisor_proposal_for_accept` row-lock. A concurrent client self-edit landing inside that window is NOT seen by the pre-flight and is silently overwritten by the accept's diff-write. The per-entity `base_version` optimistic-concurrency token NARROWS this (a stale token from before the read still conflicts) but does not ELIMINATE the read→claim gap itself. This is an inherent optimistic-concurrency characteristic, pre-existing the P2-FIX-2 work; the claim only serializes accept-vs-withdraw, not accept-vs-client-self-edit. Candidate future hardening (NOT built, out of scope): take row locks on the targeted `financial_*` rows for the duration of the accept (or move detect inside the claimed window). guard: none (doc-only; accepted optimistic-concurrency limitation)

[anti-pattern] An append-only event ledger whose "latest-event-wins" ordering tie-breaks on a RANDOM id is nondeterministic when the timestamp ties. `advisor_client_consents` (`20260528000000`) orders `created_at desc, id desc` where `id` is `gen_random_uuid()` (UUIDv4, not monotonic). Two consent events in the same transaction get the identical `now()` (transaction-start time), and same-tick single-row inserts can collide on `timestamptz` precision — so a same-tick grant+withdraw resolves by which random UUID sorts higher, i.e. a coin-flip on the consent decision (incl. the dangerous direction: a withdrawn client whose advisor retains access). The SQL predicate `advisor_can_read_client` and the TS reducer `computeConsentStatuses` (`src/data/repositories/advisor-clients.ts:~55`) agree with EACH OTHER but are both wrong, so there is no detection signal; the existing unit test uses string-sortable `id-1`/`id-2` and structurally cannot catch it. Latent only because no consent-write producer exists yet — becomes live with the Phase-2 grant/withdraw UX. Fix: a monotonic `bigint generated always as identity`/`bigserial` tie-break column (or UUIDv7), mirrored byte-identically in SQL + reducer, + a parity test with realistic lowercase-uuid ids. guard: HANDOFF.md §6 P0-C1 + the planned uuid-shaped-id parity test (PENDING — must land with the Phase-2 consent-write path; this entry is the tracking artifact until then).
