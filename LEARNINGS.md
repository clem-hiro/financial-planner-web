[gotcha] The Phase-2 ship-gate audit `verify_consent_gated_access()` must treat BOTH `user_id = auth.uid()` AND `id = auth.uid()` as valid "self" forms. `financial_profiles` PK `id` IS the auth uid (`20260410000000_init.sql:4`), so `profiles_*_own` policies key on `id`, while `financial_*` child tables key on `user_id` — `_qual_is_self_policy` therefore allowlists 16 normalized strings (8 per column × `(select )`/bare × paren/order permutations), not 8. Two coupled subtleties: (1) the normalization is `replace(regexp_replace(lower(x),'\s','','g'),'asuid','')` — the `'asuid'`→`''` step strips the `AS uid` alias Postgres injects when it rewrites `auth.uid()` as `(SELECT auth.uid() AS uid)` in `pg_get_expr` output; omit it and every real policy mis-flags. (2) Check #3 (public/anon mis-scoping, option B) exempts a policy ONLY when self-form OR consent-routed (`%advisor_can_read_client%`) — because `auth.uid()` is NULL for anon, a self/consent policy grants anon zero rows; everything else at public/anon still RAISES (precise conjunction, never a blanket pass). `_verify_consent_bypass` (check #2) is deliberately left delegating to `_qual_is_self_policy`, so extending the allowlist propagates to check #2 for free. guard: supabase/migrations/20260529000000_advisor_consent_phase2.sql (amendment block) + the embedded `select public.verify_consent_gated_access()` in supabase/tests/scratch_verify_phase2.sql + scripts/check-scratch-verify-sync.mjs (O2 byte-identity)

[correction] DB behavioral verifier pivoted from SYNTHETIC-fixture to CLONE-based (user decision). Synthesizing a client through the real `handle_new_user` access-key/QR gate inside the Supabase SQL editor cost 3 environmental iterations (P0001 access-key gate → 42701 non-idempotent re-apply → 3F000 `pg_temp` gone on a pooled/split editor connection): the editor is not a sticky single psql session, so every "synthesize the precondition" mechanism is fragile there. Removes the entire signup/access-key/handle_new_user/digest synthesis class. [convention] Migrations in this repo MUST be fully idempotent — `add column if not exists`, `create or replace function`, `drop ... if exists`, `create index if not exists`, guarded `do $$` for anything else. Reason: there is no migration ledger and migrations are hand-applied to a shared prod (the escalated no-ledger reality), so a re-apply or partial/retried apply must be safe — a non-idempotent statement aborts the hand-apply mid-file (`20260529000000`'s `alter table ... add column seq ...` raised `42701: column "seq" already exists` on a scratch re-run because the embedded copy in `scratch_verify_phase2.sql` commits and is intentionally not rolled back). Idempotent migrations also make `scratch_verify_phase2.sql` re-runnable on a dirty scratch. Guard clauses are additive only — they must not change post-apply state or behavior. guard: supabase/migrations/20260529000000_advisor_consent_phase2.sql + scripts/check-scratch-verify-sync.mjs

[gotcha] Operator-run SQL runbooks that are never CI-executed can harbor latent "won't even execute" defects that look correct on review. `advisor_consent_scenarios.sql` (S1–S11) and the embedded scenarios in `scratch_verify_phase2.sql` created synthetic clients via `pg_temp.mk_user({profile_type:client}) + pg_temp.link`, which BYPASSES `handle_new_user`'s access-key gate (`20260523000000`: a keyless `profile_type='client'` signup raises `P0001: Client signup requires an access key from your financial advisor.`). The runbooks were assumed-correct through multiple reviews but had never actually run against a real DB until a user ran the scratch verifier — it failed immediately at fixture setup. Fix: provision the client the real way — synthetic advisor → `advisor_access_keys` row → `advisor_qr_share_tokens` row (`token_hash = encode(digest(raw,'sha256'),'hex')`, digest UNqualified per the pgcrypto-in-public convention) → client signs up with `raw_user_meta_data.qr_token = raw` so `handle_new_user` atomically redeems and binds the real `advisor_user_id` linkage (`pg_temp.mk_linked_client`, mirrors `qr_redeem_scenarios.sql`). Lesson: an SQL test fixture that side-steps a trigger invariant to "set up state faster" is itself untested setup — make fixtures satisfy the same triggers production does. **Same root cause manifested THREE times before the script ran clean (P0001 access-key gate → 42701 non-idempotent re-apply → `3F000 schema "pg_temp" does not exist`)**: the script was authored for a single sticky `psql` session but the actual execution environment is the **Supabase SQL editor**, which pools/splits connections and may wrap the pasted script — so session-local `pg_temp` objects vanish on a later backend AND manual `begin/commit/rollback` for per-scenario isolation is unreliable. Holistic fix: real idempotent `public._cgp2_*` helpers (persist across backends; dropped at teardown) + isolation by UNIQUE per-scenario identities (`@cgp2.test`) and an explicit audited-FK-cascade `public._cgp2_cleanup()` (start cleanup for re-runnability + teardown), NOT transaction control. Meta-lesson: author runbook/verifier SQL for the ACTUAL execution environment (SQL editor ≠ psql: no reliable `pg_temp`, pooled/split connections, possible script-level tx wrapping) — don't assume psql semantics. guard: supabase/tests/advisor_consent_scenarios.sql (`public._cgp2_*` real helpers, no pg_temp / no begin-rollback isolation) + supabase/tests/scratch_verify_phase2.sql + scripts/check-scratch-verify-sync.mjs

[anti-pattern] An append-only event ledger whose "latest-event-wins" ordering tie-breaks on a RANDOM id is nondeterministic when the timestamp ties. `advisor_client_consents` (`20260528000000`) orders `created_at desc, id desc` where `id` is `gen_random_uuid()` (UUIDv4, not monotonic). Two consent events in the same transaction get the identical `now()` (transaction-start time), and same-tick single-row inserts can collide on `timestamptz` precision — so a same-tick grant+withdraw resolves by which random UUID sorts higher, i.e. a coin-flip on the consent decision (incl. the dangerous direction: a withdrawn client whose advisor retains access). The SQL predicate `advisor_can_read_client` and the TS reducer `computeConsentStatuses` (`src/data/repositories/advisor-clients.ts:~55`) agree with EACH OTHER but are both wrong, so there is no detection signal; the existing unit test uses string-sortable `id-1`/`id-2` and structurally cannot catch it. Latent only because no consent-write producer exists yet — becomes live with the Phase-2 grant/withdraw UX. Fix: a monotonic `bigint generated always as identity`/`bigserial` tie-break column (or UUIDv7), mirrored byte-identically in SQL + reducer, + a parity test with realistic lowercase-uuid ids. guard: HANDOFF.md §6 P0-C1 + the planned uuid-shaped-id parity test (PENDING — must land with the Phase-2 consent-write path; this entry is the tracking artifact until then).

[correction] pgcrypto lives in the `public` schema in this deployment, NOT a Supabase-typical `extensions` schema. Migrations 20260517100000/20260518000000/20260519000000 all `create extension if not exists pgcrypto;` UNqualified, and `gen_random_bytes(16)` is called unqualified under `set search_path = public` (20260517100000:557). I initially wrote `create extension … with schema extensions;` + `extensions.digest(...)` (Supabase-default assumption); reviewer/lead caught it — `with schema extensions` is a silent no-op when the extension already exists, and `extensions.digest` would have errored on every QR redeem/peek (feature-dead, fail-closed). Convention: call pgcrypto fns (`digest`, `gen_random_bytes`, `crypt`, `gen_salt`) UNqualified inside functions that `set search_path = public`; never schema-qualify with `extensions.`. Tests against pgcrypto must also be unqualified so a local Supabase-CLI DB (pgcrypto in `extensions` there) can't falsely pass while prod breaks. The only authoritative runtime check is `select extnamespace::regnamespace from pg_extension where extname='pgcrypto';` on the actual deployment DB. guard: supabase/migrations/20260523000000_qr_token_hash_and_atomic_redeem.sql + supabase/tests/qr_redeem_scenarios.sql

[anti-pattern] Tailwind v4 + Turbopack dev intermittently fails to regenerate the CSS layer for changed className strings and can drop arbitrary `[...]` utility values until a deep rebuild; an already-mounted element won't adopt new classes on a soft reload. This caused a ~6-iteration debugging loop on the QR dialog (top-left → top-pinned) where every class-based fix was correct in source but inert in the running build — JS/RSC updated via HMR (fresh tokens) while CSS stayed stale. Fix: for layout/positioning that must be reliable, use inline `style` (in the JS bundle, can't be JIT-dropped, beats UA stylesheet) or **core** utilities only (no arbitrary `[...]`); and a clean `rm -rf .next && npm run dev` + browser hard-reload after any className-only change. guard: src/features/advisor/AdvisorKeyQrShareButton.tsx (dialog centering is inline style, with a why-comment)

[anti-pattern] A client-input validation schema must accept every value-generator's format, not just production's. `clientAccessKeyInputSchema` (`^[A-F0-9]+$`) matched prod keys (32-hex from `fulfill_access_key_purchase`) but not the dev seed's `DEV-<8hex>`; every seeded-key client signup returned "Invalid access key format". It stayed hidden because the seed creates clients server-side via the admin API, bypassing the schema — so the client path was never exercised until a real QR signup. Lesson: when validation and a generator can drift, add a contract test pinning the generator's exact output against the schema. guard: src/lib/validation.test.ts (clientAccessKeyInputSchema describe block: accepts 32-hex, rejects legacy DEV-, bounds)

[anti-pattern] The shared long-lived `sandbox` branch must be reconciled with `origin/main` via **merge, never rebase** (force-push would clobber co-dev CleAyz), and sandbox→main PRs must be **squash-merged** (sandbox carries iteration churn). PR #6 was merged as a regular merge commit despite the recorded instruction, putting 6 dialog-iteration commits individually on `main` — irreversible without a destructive `main` rewrite. SOP: optional pre-PR `merge origin/main`→sandbox if conflicts; PR; **squash-merge**; mandatory post-merge back-merge `origin/main`→sandbox to re-sync (squash always re-diverges the branches by construction). guard: HANDOFF.md §5/§References (merge-not-rebase SOP + squash-merge requirement recorded)

[gotcha] One Supabase project is shared by localhost dev AND Vercel production. Consequences seen this session: dev-seeded `DEV-` keys polluted prod; the `Confirm Email` toggle is project-global (can't be OFF for local + ON for prod); `getSiteOrigin()` + Supabase Auth Site URL/Redirect URLs must be kept consistent across both. The standing recommendation (separate dev/prod Supabase projects) is a HANDOFF §6 P1 flagged for an explicit user decision.

[gotcha] Tests that mutate `process.env` / module-shared state (e.g. `src/lib/site-origin.test.ts` reassigns `process.env` and a shared `currentHeaders`) are correct only because Vitest's default per-file process isolation holds; nothing pins `pool`/`isolate` in `vitest.config.ts`.
